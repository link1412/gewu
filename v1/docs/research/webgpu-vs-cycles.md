# WebGPU path tracing vs. Cycles as a reusable skill dependency

Research cut-off: **2026-10-28**. Primary-source desk review; no renderer binary, installer or wheel was downloaded or executed. `[sourced]` means the linked source states the fact (including clearly identified author benchmarks); `[inferred]` means our interpretation or a limited search finding. “Not found” is not proof that a feature cannot exist. Recommendations are research conclusions, not measured results on our scenes.

## Short answers

1. **Browser WebGPU: no exposed hardware ray tracing; native Rust wgpu: experimental hardware ray queries are available.** [inferred] The browser standard still lacks the entry points; October 2026 acceleration-structure/ray-query work remains proposals. [sourced] Native wgpu has Metal, DX12 and Vulkan implementation evidence, including merged Metal support. [WebGPU proposal](https://github.com/gpuweb/gpuweb/issues/11055), [wgpu Metal implementation](https://github.com/gfx-rs/wgpu/pull/8071), [backend status](https://github.com/gfx-rs/wgpu/issues/6762).

2. **Do not replace the film renderer on feature lists alone.** [inferred] MuTracer is the most relevant browser candidate in this survey, with bounded interior scattering; current three-gpu-pathtracer has migrated to WebGPU. Neither inspected project establishes quality parity for the requested glaze/crackle/fibres or a ready-made unattended EXR film workflow. [MuTracer materials](https://github.com/pissang/mutracer/blob/main/docs/materials.md), [MuTracer output API](https://github.com/pissang/mutracer/blob/main/docs/api.md), [three migration](https://github.com/gkjohnson/three-gpu-pathtracer/releases/tag/v0.0.25), [three outstanding work](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777).

3. **Published numbers suggest potentially large traversal costs, but no defensible universal speed ratio.** [inferred] A small sphere-scene author benchmark implies WebGPU 30–33× slower than Vulkan RT; [sourced] a recent simplified ray-tracing paper reports 9–27× versus OptiX. [inferred] Neither predicts an M4 Pro macro-film render: the first lacks software BVH traversal and the second excludes multibounce indirect light. No matched WebGPU–MetalRT film benchmark was found. [Sphere benchmark](https://github.com/TwentyFiveSoftware/webgpu-ray-tracing#performance), [shader](https://github.com/TwentyFiveSoftware/webgpu-ray-tracing/blob/main/src/raytracing/shaders/compute.wgsl), [paper/Table 2/AppendixB](https://arxiv.org/html/2610.28950v1).

4. **Keep pinned Blender/Cycles as the production default.** [inferred] It already provides background Python rendering and native GPU selection; replacing it moves substantial renderer and automation work into the skill. [inferred] Rounded package sizes are 346.3 MB macOS ARM64, 385.3 MB Linux x64 and 405.8 MB Windows x64 portable ZIP. [sourced] M4 Pro has hardware RT. Distributed scripts using `bpy` have a GPL-compliance boundary; purely external launchers are different. [CLI](https://docs.blender.org/manual/ka/latest/advanced/command_line/arguments.html), [archive byte counts](https://download.blender.org/release/Blender5.2/), [M4 Pro](https://support.apple.com/en-us/121553), [license](https://www.blender.org/about/license/), [FAQ](https://www.blender.org/support/faq/).

5. **Mitsuba 3 is a serious Python/spectral alternative, and now runs on Apple GPUs.** [sourced] `pip install mitsuba`, spectral/polarized variants, CUDA/OptiX and the 3.9-series Metal backend are documented. [inferred] Old “NVIDIA GPU only / no Apple GPU” advice is obsolete; pin a release and query installed variants because official pages disagree about the variant list. [Install](https://mitsuba.readthedocs.io/en/latest/), [variants](https://mitsuba.readthedocs.io/en/v3.9.1/src/key_topics/variants.html), [Metal release](https://mitsuba.readthedocs.io/en/v3.9.1/release_notes.html), [quickstart](https://mitsuba.readthedocs.io/en/latest/src/quickstart/mitsuba_quickstart.html).

### Native Rust wgpu: verified implementation and caveat

- [sourced] `EXPERIMENTAL_RAY_QUERY` is labeled “This is a native-only feature.” and “THIS IS EXPERIMENTAL”. [wgpu 30.0.1 docs](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html#associatedconstant.EXPERIMENTAL_RAY_QUERY).
- [sourced] **Documentation inconsistency:** the same current rustdoc lists only Vulkan under supported platforms. Tagged implementation and merged PR establish Metal/DX12 too; therefore use implementation evidence and state the discrepancy explicitly. [rustdoc](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html#associatedconstant.EXPERIMENTAL_RAY_QUERY), [tracking issue](https://github.com/gfx-rs/wgpu/issues/6762), [Metal PR](https://github.com/gfx-rs/wgpu/pull/8071).
- [sourced] PR #8071, merged February 18, 2026: “Implements the missing ray tracing acceleration structures in the HAL metal backend.” The author reports working scene, shadow, cube and triangle examples in compute and fragment shaders. [PR #8071](https://github.com/gfx-rs/wgpu/pull/8071).
- [sourced] In v30.0.1, Metal adapter checks macOS 15/iOS 18/tvOS 18/visionOS 2+, `supportsRaytracing()` and `supportsRaytracingFromRender()` (lines 1119–1128), then sets `EXPERIMENTAL_RAY_QUERY` (line 1280). [tagged Metal source](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/metal/adapter.rs).
- [sourced] Naga translates to `metal::raytracing::intersection_query` (lines 18–22); backend command code calls native `buildAccelerationStructure_descriptor_scratchBuffer_scratchBufferOffset` (lines 1744–1770). This verifies native API use beyond feature advertisement. [tagged Naga MSL implementation](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/naga/src/back/msl/ray.rs), [tagged Metal build commands](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/metal/command.rs).
- [sourced] DX12 enables ray query for DXR Tier 1.1+ and shader model 6.5+ (lines 571–581); Vulkan requests `VK_KHR_ray_query` plus acceleration structure dependencies (lines 1295–1307). [tagged DX12](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/dx12/adapter.rs), [tagged Vulkan](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/vulkan/adapter.rs).
- [sourced] Ray tracing pipelines should not be conflated with ray queries: the wgpu API spec calls pipelines “currently in development”; release source has an experimental pipeline feature flag, but a feature flag alone establishes no complete portable implementation. [wgpu RT design](https://github.com/gfx-rs/wgpu/blob/trunk/docs/api-specs/ray_tracing.md), [tagged feature definitions](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-types/src/features.rs).
- [sourced] Apple says “Hardware-accelerated ray tracing transparently benefits apps that already use Metal's ray tracing APIs”. Apple recommends the intersector API over the intersection-query API where possible for maximum hardware benefit. [Apple GPU talk](https://developer.apple.com/videos/play/tech-talks/111375/). [inferred] Thus native wgpu inline-query hardware access does not imply matching a tuned native Metal renderer's performance.
- [sourced] Apple May 21, 2026 tables list Metal RT compute/render support from Apple6 and identify M1=Apple7, M2=Apple8, M3=Apple9; the M3 announcement says hardware ray tracing came to Mac “for the first time.” [feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf), [M3 announcement](https://www.apple.com/ie/newsroom/2023/10/apple-unveils-m3-m3-pro-and-m3-max-the-most-advanced-chips-for-a-personal-computer/). [inferred] API support on M1/M2 is therefore not dedicated hardware traversal support.

### Implication for the skill

[inferred] A browser WebGPU replacement sacrifices access to dedicated RT acceleration today; native Rust wgpu can avoid that sacrifice but becomes a separately built native renderer dependency and still needs the material/integrator/denoising/validation work. RT capability itself cannot establish craft-material fidelity. [browser proposal state](https://github.com/gpuweb/gpuweb/issues/11055), [native implementation](https://github.com/gfx-rs/wgpu/pull/8071).

## Decision for this skill and a falsifiable next step

[inferred] Choose **Blender/Cycles for final frames, optionally MuTracer for browser previews**, and evaluate Mitsuba as a separate spectral/reference dependency. Browser delivery can reduce end-user installation friction when an interactive web view is the goal. For an AI agent already driving a local renderer, a one-time Blender package is unlikely to outweigh reimplementing missing transport, fibre, animation and output behavior. No comparable total-cost or render-cost measurement was found; this recommendation is about the documented integration gap. [Blender automation](https://docs.blender.org/manual/ka/latest/advanced/command_line/arguments.html), [three outstanding work](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777), [MuTracer API](https://github.com/pissang/mutracer/blob/main/docs/api.md), [Mitsuba Metal](https://mitsuba.readthedocs.io/en/v3.9.1/release_notes.html).

[inferred] Hardware RT accelerates intersection work; it does not by itself supply a correct material or integrator. Conversely, software traversal does not inherently prevent photorealism. The decision must compare implemented transport and time to equivalent quality, rather than “WebGPU versus native” labels. [pbrt transport model](https://pbr-book.org/4ed/Volume_Scattering/Media), [native ray-tracing mechanism](https://arxiv.org/html/2610.28950v1#S3.SS1).

[inferred] For the glaze, distinguish **volume scattering bounded by refractive surfaces** from absorption-only tinted glass, an unbounded fog demo, a surface clearcoat, or an SSS approximation. pbrt explicitly models interior/exterior media and dielectric interfaces. A 1–2 mm layer over an opaque dark body, with geometry inside it, should be a dedicated regression scene; a named “SSS” feature alone is insufficient evidence. MuTracer's single medium state warrants testing boundary ordering and reflections at the body. [pbrt medium interfaces and Fig 11.16](https://pbr-book.org/4ed/Volume_Scattering/Media), [MuTracer medium code](https://github.com/pissang/mutracer/blob/main/src/renderer/wgsl/chunks/sampleMaterial.wgsl.ts).

[inferred] If browser finals remain attractive, test a bounded prototype after this desk review: (1) a glaze slab with embedded crackle and a dark backing, (2) a silk-fibre patch at final macro magnification, and (3) enamel/gold under the intended studio lights. Compare undenoised linear images at converged sampling with pbrt/Mitsuba/Cycles using matched geometry, units, lights, BSDFs and color transforms; separate RGB-model error from integrator error. Then inspect a short moving-camera sequence for highlight/denoiser instability and verify scripted float output and completed-GPU wall time on the M4 Pro. These are proposed acceptance tests, not tests run here. [pbrt media](https://pbr-book.org/4ed/Volume_Scattering/Media), [reference-renderer comparison harness](https://github.com/gkjohnson/three-gpu-pathtracer/blob/main/example/viewerTest.js), [float-output semantics](https://github.com/pissang/mutracer/blob/main/docs/api.md).

[inferred] Stop that prototype if required material behavior or deterministic scene-linear export is unavailable without building major renderer subsystems, or if it fails the team's chosen image-quality/time budget. Native wgpu can access RT but still requires building those subsystems; it is an engine-development option, not demonstrated simplification of this skill. [wgpu Metal](https://github.com/gfx-rs/wgpu/pull/8071), [three remaining features](https://github.com/gkjohnson/three-gpu-pathtracer/issues/777).
